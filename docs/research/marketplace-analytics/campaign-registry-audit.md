## 1. Что подтверждено кодом

Единственная запись в `ref.campaigns` — `_write_tenant_campaigns`.

`src/profitsamurai/registry.py`, строки 275–310. Для каждого кабинета из ответа выполняется `INSERT ... ON CONFLICT (campaign_id) DO UPDATE` полей `business_id` и `placement_type`. Затем удаляются только строки того же `business_id`, чьих `campaign_id` нет в новом наборе. Другой `business_id` этот `DELETE` не трогает.

Вызов идёт из `attach_shops`, строки 138–190 того же файла. Сначала в служебной таблице `shops` пишется или обновляется строка клиента, маркетплейса и `business_id`. Потом кампании пишутся в базу этого клиента. Повтор того же кабинета заменяет его ключ и статус на `connected`.

Маршрут `POST /clients/{client_id}/shops` в `src/profitsamurai/api/routers/clients.py`, строки 90–112, перед записью вызывает `fetch_campaigns`. Это `GET /v2/campaigns`, `src/profitsamurai/integrations/yandex_market/campaigns.py`, строки 41–70. Кампания без `business.id` пропускается.

Чтение для импорта фильтрует кабинет. `clients.py`, строки 143–148: из `read_tenant_campaigns` берутся только строки, у которых `business_id` равен `shop.business_id`. Сама `read_tenant_campaigns`, `registry.py`, строки 406–424, такого фильтра не имеет и возвращает все строки `ref.campaigns`.

Первичный ключ таблицы — только `campaign_id`. Миграция `migrations/tenant/versions/001_tenant_schema.py`, строки 18–26. Колонки `shop_id`, `created_at` и `updated_at` миграция не создаёт. `group_campaigns` в `src/profitsamurai/campaign_groups.py`, строки 15–27, оставляет один `business_id` на `campaign_id`: при повторе побеждает последняя строка ответа.

ADR `docs/adr/0002-shop-reads-campaign-list.md`, строка 17, фиксирует то же правило: повтор кабинета заменяет его кампании, кабинет, которого больше нет в ответе ключа, сам не удаляется.

Интеграционный тест `tests/integration/test_clients.py`, строки 59 и 128–137, использует номера `41` и `42` и кабинет из диапазона `8100000000 + (uuid4 % 1000000)`. Тест создаёт нового клиента с именем `Acme` и в `finally` удаляет его базу. Изоляция в `tests/integration/isolation.py`, строки 41–44 и 54–59, запрещает этому тесту рабочий кластер `localhost`/`postgres` на порту 5432 и базы `client_*`.

## 3. Что найдено в Git-истории

Коммит `4e45e8a` добавил запись кампаний и тест с номерами `41` и `42`. Самих строк рабочей базы в Git нет: справочник не сидируется.

Запись в рабочую базу сделал разовый скрипт прошлой сессии сброса кластера. Он вызвал `attach_shops` для клиента `7fa5a7ae-7619-407b-a599-c5456571750d` со списком `RemoteCampaign(8100000041, 41, FBS)` и `RemoteCampaign(8100000041, 42, FBY)`. Скрипт во временном файле `reset_attach_shop.py` копировался в контейнер API и запускался там. Итог той сессии: магазин подключён через ту же функцию, что и маршрут, запрос в Яндекс не отправлялся, потому что ключа продавца на этом шаге не было. Затем к этому клиенту подключили кабинет `173963462`. Строки `8100000041` остались.

Номера `41` и `42` совпадают с тестом. Число `8100000041` в скрипте задано явно. Тест вычисляет кабинет случайно и пишет его в новую базу `Acme`, не в `RESET_CLIENT_A`.

## 4. Наиболее вероятное происхождение

Это проверочная запись после сброса кластера, а не ответ Яндекса и не прогон интеграционного теста по рабочей базе.

Факт: в реестре есть магазин `8100000041` со статусом `connected`, в справочнике ровно две его кампании с моделями FBS и FBY, финансовый журнал их не использует, скрипт сессии сброса вызывает `attach_shops` с этими тремя числами и не ходит в API.

Гипотеза, которая не нужна для вывода: длина 100 байт совпадает и с коротким проверочным секретом того скрипта, и с любым другим секретом не длиннее 16 байт. Расшифровка не делалась.

Неизвестно, вызовет ли кто-то `attach_shops` с этими номерами ещё раз. Текущий код такого повтора сам не делает.

## 6. Риск смешивания

Клиенты изолированы базами. Клиент B этих кампаний не содержит.

Внутри клиента A кабинеты лежат в одной таблице без `shop_id`. Это не авария синхронизации. `attach_shops` записывает каждый кабинет из переданного списка. Повторный ответ ключа удаляет лишние кампании только своего `business_id`. Поэтому обычное обновление кабинета `173963462` не сотрёт `41` и `42`, а подключение второго ключа добавит второй кабинет.

Импорт финансов уже не смешивает кабинеты: он оставляет кампании с `business_id` магазина. Двадцать импортов клиента A это подтверждают. Соединение `report_imports.campaign_id` с первичным ключом `ref.campaigns` для этих импортов вернёт `129958161` и `148633332`, не `41` и `42`.

Смешение появится, если представление или отчёт прочитают всю `ref.campaigns` без фильтра кабинета. Тогда в списке кампаний клиента A будут проверочные `41` и `42`. На уже сохранённые строки отчётов это не влияет.

Отдельное ограничение структуры: `campaign_id` уникален на всю базу клиента. Два кабинета не могут хранить один и тот же номер. Повторная запись того же номера сменит `business_id` через `ON CONFLICT`. Для номеров `41` и `129958161` столкновения нет.

## 7. Что может понадобиться перед представлениями

Миграция и удаление строк не требуются, чтобы первые представления не увидели проверочный кабинет. Достаточно брать модель размещения по `campaign_id` уже отфильтрованного импорта, а не выводить все строки `ref.campaigns`. Импорт такой фильтр уже применяет.

Отдельная таблица на кабинет или `shop_id` в справочнике понадобятся только если один клиент должен штатно держать несколько живых кабинетов и экран обязан показывать их списком. Сейчас это не условие для расчёта по импортам магазина `173963462`.

Удаление магазина `26d23c65-008f-47c9-86bf-13eacceacad5` и кампаний `41`, `42` остаётся отдельным решением. Этот отчёт его не выполняет.
