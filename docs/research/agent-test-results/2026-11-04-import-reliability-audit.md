# Аудит надёжности импорта финансовых отчётов

Дата: 2026-11-04. Read-only. Python, SQL, миграции, конфигурация, тесты, `LESSONS.md`, ADR, `ROADMAP.md` и бизнес-правила не менялись. Повторный импорт не запускался. Существующие строки не удалялись и не обновлялись. Git commit не делался.

## 1. Краткий итог

Импорт не перезаписывает уже сохранённые версии. Повтор того же периода получает новый `version`, старые ZIP и строки остаются. Строка таблицы связана с попыткой через `import_id`, попытка — с одним исходным файлом. В живой базе клиента это подтверждено: 20 попыток, все `done`, у каждой ровно один файл, `row_count` совпадает с числом строк, `byte_size` совпадает с длиной `bytea`, все 20 файлов начинаются с ZIP-сигнатуры `504b0304`. Версии октября 1–4 лежат рядом.

Запись не идемпотентна в смысле «повтор ничего не создаёт»: каждый успешный запуск добавляет полный новый комплект. Технические повторы запуска и повторяющиеся строки внутри исходного JSON — разные явления. Парсер повторы из источника не удаляет.

Критических дыр, при которых новый импорт затирает старый файл или старые строки, нет. Есть узкое окно, где сбой после уже зафиксированных строк может записать попытку как `failed` с `row_count = 0`, и есть зависший статус `running`, если процесс умрёт между `begin` и `finish`. В текущих данных таких строк нет.

Дедупликацию строк отчёта до ответа поддержки Яндекс Маркета вводить нельзя. Этот аудит её не предлагает.

## 3. Текущая схема процесса импорта

Один `POST /clients/{client_id}/shops/{shop_id}/finance-imports` на календарный месяц.

1. `import_shop_finance` берёт сессионный `pg_try_advisory_lock` на магазин (`clients.py`, около строк 154–166; ключи в `advisory_keys`, `finance.py` 103–108).
2. `import_reports` один раз читает `max(version) + 1` по магазину и периоду (`finance.py` 186, `SqlReportStore.next_version` 22–36). Этот номер общий для всех отчётов запуска.
3. На каждую кампанию строится `goods_realization`, затем один `marketplace_services` и один `united_netting` (`build_report_requests`, `reports.py` 99–161).
4. Для каждого отчёта `begin` сразу коммитит строку `raw.report_imports` со статусом `running` (`finance_store.py` 38–70).
5. Генерация идёт с `idempotent=False` (`_generate`, `finance.py` 391–406). Потерянный ответ generate не постится снова. Следующие отчёты этого запуска помечаются `failed` с текстом `previous report generation result is unknown` и в Маркет уже не отправляются (`_blocks_next` 329–333, `_not_requested` 336–356).
6. При `DONE` байты ответа пишутся в `raw.report_files` отдельным коммитом, затем парсятся, затем строки пишутся в `raw.report_rows` отдельным коммитом, затем `finish` ставит `done` и `row_count = len(rows)` (`_import_one`, `finance.py` 282–286).
7. Блокировка снимается в `finally` (`hold_import_lock` 136–142), в том числе когда импорт бросает исключение. Соединение блокировки — отдельное, `AUTOCOMMIT`, `NullPool` (`tenant_import_lock` 145–157). Запись отчётов идёт другими соединениями `SqlReportStore`.

Чтение `raw.report_rows` в приложении есть только у записи. Слоя, который сам склеивает версии в прибыль, в коде нет.

## 4. Результаты по шести направлениям

### 4.1. Повторные импорты и версии

Подтверждённые факты.

- Новая версия — это `max(version) + 1` по `shop_id`, `period_from`, `period_to`. Статус прошлых попыток на номер не влияет: в максимум входят и `failed`, и `running`.
- Предыдущие версии код не удаляет и не обновляет. `save_file` только вставляет новую строку. `finish` меняет поля статуса той же попытки, не `content` и не `payload`. Удаления импорта в этом пути нет. Каскад `ON DELETE CASCADE` сработает только если строку `report_imports` удалит кто-то другой; импорт этого не делает.
- Уникальность попытки: `UNIQUE NULLS NOT DISTINCT (shop_id, period_from, period_to, report_type, campaign_id, version)`. В живой базе ограничение так и называется: `uq_report_imports_version`. Две реализации разных кампаний могут иметь один `version`. Два `marketplace_services` одного периода и версии не могут: `campaign_id` NULL для них неразличимы.
- Связь: `report_rows.import_id` → `report_imports.id` → ровно один `report_files.import_id` (`UNIQUE (import_id)`). В строке попытки лежат магазин, кабинет, тип, период, кампания, версия, `yandex_report_id`, `started_at`, `finished_at`, статус.
- Конкретная строка определяется попыткой, полем `sheet` и `row_number`. `row_number` — порядковый номер во всей попытке, с 1, сквозь все листы (`finance_store.py` 92–101), как и написано в `docs/data-model.md`. Имя листа — имя JSON-файла внутри ZIP без каталога и без суффикса `.json` (`reports.py` 274).

Живые данные, один `shop_id`:

| Период | Версия | Состав | Сумма `row_count` |
| --- | ---: | --- | ---: |
| 2026-09-01 | 1 | 2 реализации, услуги, взаиморасчёты, все `done` | 254 + 925 + 2521 |
| 2026-10-01 | 1 | тот же состав, все `done` | 59 + 221 + 561 |
| 2026-10-01 | 2 | тот же состав, все `done` | 118 + 221 + 561 |
| 2026-10-01 | 3 | тот же состав, все `done` | 118 + 221 + 561 |
| 2026-10-01 | 4 | тот же состав, все `done` | 118 + 221 + 561 |

Версия 1 октября по-прежнему на месте рядом с версиями 2–4. Разная сумма строк реализации (59 и 118) здесь только факт хранения. Это не вывод о том, как такие строки учитывать.

Что в метаданных нет, хотя байты файла это позволяют восстановить:

- путь метода API и `format=JSON` колонками не пишутся; тип отчёта задаётся в `build_report_requests`;
- подписанный URL файла не пишется (`docs/data-model.md`);
- отдельной отметки «момент скачивания» нет: `started_at` ставится в `begin` до генерации, `finished_at` — в `finish`;
- SHA-256 файла колонкой не хранится. Есть `byte_size`.

Сопоставить строку с исходным JSON можно: взять ZIP этой `import_id` и разобрать его тем же порядком, что `parse_report_bytes`. `payload` — `jsonb`, это значения разобранной строки, не дословная копия текста JSON. Порядок ключей jsonb не хранит. Неизменённый оригинал — `report_files.content`.

Потенциальный риск. Два JSON в разных каталогах ZIP с одним именем файла получат один и тот же `sheet`. `row_number` их всё же различает. В этой проверке состав имён внутри архивов заново не разбирался.

### 4.2. Идемпотентность

Подтверждённые факты.

- Повторный POST того же периода не ищет уже готовую версию и не останавливается. Он создаёт следующую версию и заново заказывает отчёты. Случайной второй копии внутри того же `import_id` путь записи не делает: `begin` всегда новый UUID, `save_rows` вызывается один раз.
- Повторяющиеся объекты внутри исходного JSON остаются. `as_object_list` (`jsonutil.py` 41–48) складывает каждый JSON-объект, без сравнения с соседями. Отдельного шага дедупликации нет.
- Частичный запуск по отчётам одного вызова делит один `version`. Успешный отчёт остаётся `done` со своими строками. Неуспешный — своя строка `report_imports` со статусом `failed`, `no_data` или `too_large`. Это не смешение строк разных версий: у строк разных отчётов разные `import_id`.
- Если generate оборвался так, что ответ мог не дойти (`httpx.TransportError`, `TransientStatusError`, `ReportTimeout`, HTTP 499), остальные отчёты этого запуска не запрашиваются (`_blocks_next`). Они всё равно занимают этот `version` записями `failed` без файла.
- Повтор после ошибки для уже записанных данных безопасен в том смысле, что старые файлы и строки не затираются. Он не продолжает зависшую строку `running`, а открывает новый `version`. Недоделанная попытка остаётся как есть.
- Смешать строки разных версий записью текущий код не может: `save_rows` пишет только в новый `import_id`. Смешает чтение, если выбрать «последний успешный отчёт каждого типа» из разных `version` или сложить все версии периода. Такого чтения в приложении нет.

Окно частично записанной попытки, по границам коммитов:

| Место обрыва | Файл | Строки | Что делает обработчик исключения |
| --- | --- | --- | --- |
| До скачивания | нет | нет | `failed`, `row_count = 0` |
| После `save_file`, на разборе | есть | нет | `failed`, `row_count = 0`; текст `ReportParseError` короткий и без секретов (`public_error`) |
| `save_rows` не закоммитился | есть | нет | `failed`, `row_count = 0` |
| После коммита `save_rows`, если `finish` бросает исключение | есть | есть | тот же `except` ставит `failed` и `row_count = 0` (`finance.py` 288–297) |
| Процесс убит после `begin` и до `finish` | как успели записать | как успели записать | статус остаётся `running`, `row_count` остаётся 0, пока `finish` не вызван |

Последние две строки — потенциальный риск, не наблюдение в базе. Сейчас `running` нет, расхождений `row_count` и `count(report_rows)` нет.

Пустой разбор — не ошибка. Если ZIP скачался и парсер вернул 0 строк, попытка становится `done` с `row_count = 0`. Статус `no_data` ставится только когда так ответил опрос генерации, до скачивания.

### 4.3. Параллельные запуски

Подтверждённые факты.

- Блокировка есть: сессионные `pg_try_advisory_lock` / `pg_advisory_unlock`, два `int4` из SHA-256 строки `finance-import:{shop_id}`. Это не `pg_advisory_xact_lock` и не блокировка строки `report_imports`.
- Ключ зависит только от магазина. Второй импорт того же магазина, в том числе другого месяца, получает `FinanceImportBusy` и HTTP 409 `finance import is already running`. До `next_version` и `begin` он не доходит, строк не создаёт.
- Разные магазины получают разные ключи. Тест проверяет неравенство ключей двух UUID. Одновременный импорт двух магазинов кодом не сериализуется. Общего лимита на все магазины нет. Лимит генерации одного метода (пауза 120 секунд) считается внутри одного запуска.
- `finally` вызывает unlock. Неудачный повторный захват на том же соединении unlock не вызывает, чтобы не снять чужой замок: исключение бросается до `try` (`hold_import_lock` 130–135). Тест `test_parallel_import_of_the_same_shop_period_is_rejected` это фиксирует и ждёт один unlock.
- Аварийное завершение процесса отпускает сессионный advisory lock вместе с сессией PostgreSQL. `idle_session_timeout` на этом сервере 0, то есть сам сервер сессию по простою не режет. Сейчас advisory lock в базе нет (`pg_locks`, 0).
- Замок и запись — разные соединения. Если соединение замка оборвётся, а процесс записи жив, второй запуск теоретически сможет войти, пока первый ещё пишет. Уникальный ключ версии тогда остановит вторую вставку того же номера, но первая попытка уже могла заказать отчёты в Маркете. Это потенциальный риск, не воспроизводился.

Предположение. Коллизия 64 бит ключа между двумя магазинами практически недостижима. Проверкой всех пар магазинов это не доказывалось: в базе с финансовыми таблицами магазин один.

### 4.4. Сохранение исходных данных

Подтверждённые факты.

- Оригинальные байты пишутся как пришли из `download_report_file`: лимит размера, проверка HTTPS, без перепаковки (`reports.py` 217–245, 311–314; `save_file` 72–82).
- JSON-файлы отдельно таблицей не лежат. Они остаются внутри ZIP в `content`. Разбор копирует объекты строк в `jsonb` и исходный `bytea` не меняет.
- Повторное сопоставление возможно по `import_id` + порядок `parse_report_bytes`. Для 20 текущих файлов магия `504b0304`, `byte_size = octet_length(content)`, файл ровно один, попыток без файла нет.
- В попытке сохраняются тип отчёта, период, кампания (для реализации), `business_id`, `shop_id`, версия, идентификатор генерации Маркета, начало и конец попытки, статус, `row_count`, короткий `error_message`. У всех 20 текущих попыток `yandex_report_id` и `finished_at` заполнены, `error_message` пуст, `row_count > 0`.

Потенциальный риск. Элемент JSON-массива, который не объект, `as_object_list` пропускает. В ZIP он останется, в `report_rows` его не будет, и `row_count` его не учтёт. Долю таких элементов в уже скачанных файлах этот аудит не считал.

### 4.5. Контроль качества импорта

Что уже есть:

| Проверка | Где |
| --- | --- |
| Статус попытки | `running`, `done`, `no_data`, `too_large`, `failed`; CHECK в миграции и в живой базе |
| `row_count` | число объектов, которые вернул парсер, пишется в `finish` |
| `error_message` | короткий текст без ключа API и без URL файла |
| `byte_size` | `len(content)` в момент вставки |
| Один файл на попытку | `UNIQUE (import_id)` |
| Тип отчёта | CHECK на три известных типа |
| Календарный месяц | `FinanceImportCreate` и `require_calendar_month` |
| Размер скачивания и ZIP | отказ до записи, если тело больше лимита или архив не читается / слишком велик на разжатии |
| Устойчивость к одному плохому отчёту | остальные отчёты запуска продолжаются, если ошибка не из `_blocks_next` |

Чего нет:

- отдельного подсчёта строк в исходном JSON после записи и сверки с `count(*)` из `report_rows`;
- сохранённых количеств по листам;
- сумм денежных полей и сверки этих сумм с файлом;
- сохранённой контрольной суммы (SHA-256 или иной);
- таблицы предупреждений;
- запрета `done` при нуле строк после успешного скачивания;
- проверки, что `byte_size` совпадает с длиной `bytea` (сейчас это следствие одной вставки, не ограничение базы);
- уникальности `(import_id, sheet, row_number)`.

В живой базе сверка, которой нет в коде, сейчас сходится сама: 20 `done`, 0 расхождений `row_count` и числа строк, 0 расхождений `byte_size` и `octet_length`, 0 повторов `row_number` внутри попытки. Это наблюдение по уже записанному, не работающая проверка импорта.

## 5. Риски

### Critical

Нет. Путь импорта не заменяет `content` и `payload` уже записанной версии. В базе версии 1–4 октября сосуществуют, файлы на месте.

### High

Сбой `finish` после уже закоммиченных `report_rows` помечает попытку `failed` и `row_count = 0`, хотя файл и строки остались (`finance.py` 284–297). Кто поверит статусу и счётчику, не увидит записанные строки. В текущих 20 попытках расхождений нет: риск в коде, не в уже лежащих данных.

### Medium

- Убитый процесс оставляет `running` навсегда. Следующий запуск из-за этого не блокируется: замок сессионный и после обрыва соединения исчезает, а `next_version` просто берёт следующий номер. Зависшая попытка может иметь файл и строки при `row_count = 0`. Сборщика таких попыток нет. Сейчас строк `running` нет.
- Одна версия может быть неполной: часть отчётов `done`, часть `failed`, либо хвост не создан, если исключение вылетело из `finish`. Безопасное чтение — целиком один `version`, у которого нужные отчёты в `done`. Сборка «последний успешный тип из разных версий» смешает снимки. Приложения, которое так читает, нет.
- Повтор после оборванного generate снова закажет отчёты в Маркете. Локальные старые байты это не портит. Заказ в Маркете мог ещё считаться незавершённым. Так задумано в `_blocks_next`, отдельной проверки «генерация ещё идёт» нет.
- Не-объекты в JSON молча не попадают в `report_rows`. Пустой разбор скачанного файла становится `done` / 0.
- Нет хранимой контрольной суммы. Подмена или порча `bytea` кодом импорта не детектируется; длина сейчас совпадает у всех 20 файлов.
- Параллельные магазины не делят замок и могут одновременно попасть в лимит генерации одного API-ключа, если ключ общий. Сейчас финансовые таблицы есть у одного магазина.
- Тесты не доходят до Postgres, поэтому уникальный ключ, границы коммитов и зависший `running` автоматикой не ловятся.

### Low

- Обрыв только соединения advisory lock при живом процессе записи. `idle_session_timeout` это не провоцирует: он 0.
- Нет уникальности `(import_id, sheet, row_number)`. Второй `save_rows` по тому же `import_id` мог бы продублировать номера. В коде вызов один. В базе повторов номера нет.
- Одинаковое имя JSON в разных каталогах ZIP схлопнет `sheet`.
- `jsonb` не хранит порядок ключей. Для сверки «байт в байт» с исходным текстом нужен ZIP, не `payload`.

Коротко: новая версия и сохранность байтов на памяти, продолжение после ошибки одного отчёта, запрет второго POST после потерянного generate, отказ второго advisory lock того же магазина, различие ключей другого магазина, календарный месяц, статусы опроса, лимит размера скачивания, отсутствие API-ключа на скачивании файла. Прогон 14 тестов файла прошёл.

## 7. Каких проверок нет

В импорте нет сверки числа строк файла и базы, количеств по листам, денежных сумм, контрольной суммы, предупреждений и запрета статуса `done` при пустом разборе. В тестах нет Postgres, обрыва между коммитами, повтора после сбоя, двух периодов одного магазина, реального параллельного второго магазина и случая двух одинаковых объектов в исходном JSON.

## 8. Рекомендации без внесения изменений

Их можно делать позже отдельной задачей. В этот аудит они не входят.

- Оставить хранение каждой версии и каждого исходного повтора как есть, пока нет правила от поддержки.
- Для любого будущего чтения договориться: одна версия целиком, только нужные статусы `done`, без объединения типов из разных версий и без сложения всех версий периода.
- В коде, отдельным изменением: если строки уже закоммичены, не записывать `row_count = 0` поверх них; сверять `count(*)` и повторный разбор сохранённого ZIP до `done` и при расхождении оставлять файл и строки, помечая ошибку сверки.
- Хранить SHA-256 рядом с `byte_size`. Это уже миграция.
- Добавить тесты на границы `SqlReportStore`, зависший `running`, повтор после `failed`, два одинаковых объекта в ZIP, 409 на второй период того же магазина. Существующие тесты не менять вперемешку с финансовой логикой дублей.
- Наблюдать `status = 'running'` при свободном advisory lock только чтением. Не закрывать и не удалять такие строки, пока нет отдельного решения: у них может уже лежать файл.

## 9. Что нельзя решать до ответа поддержки

- Удалять, сливать или пропускать повторяющиеся строки внутри отчёта реализации или любого другого отчёта.
- Считать расхождение сумм строк октября (версия 1: 59 по двум реализациям, версии 2–4: по 118) ошибкой импорта или поводом переписать старую версию. Обе величины лежат в базе как разные снимки.
- Менять парсер так, чтобы он выбрасывал «лишние» объекты.
- Выбирать, какая версия финансово верная.
- Вводить идемпотентность вида «если за период уже есть `done`, новый файл не сохранять», если целью является не скачивать повтор. Это уже другое правило хранения, не исправление дублей внутри файла, но оно помешает сохранять следующий снимок, пока поддержка не объяснит, какой снимок полный.

## Разделение выводов

Подтверждено кодом и базой: версии не затираются; строка прослеживается до одного ZIP через `import_id`; замок магазина есть и на ошибке Python снимается в `finally`; повтор периода создаёт новую версию; внутри файла дедупликации нет; текущие 20 попыток согласованы по счётчику, файлу и длине.

Потенциальный риск: ложный `failed` / `row_count = 0` после успешного `save_rows`; вечный `running` после убитого процесса; смешение версий только на стороне будущего чтения; тихий пропуск не-объектов JSON.

Предположение: обрыв TCP именно соединения замка при живой записи маловероятен при `idle_session_timeout = 0`, но кодом не закрыт.

Нужна отдельная проверка, не блокирующая этот вывод: есть ли в уже сохранённых ZIP элементы массивов не-объекты; почему у второй базы клиента нет `raw.report_imports` (к надёжности уже выполненных 20 попыток это не относится); ответ поддержки о повторяющихся строках отчёта.
